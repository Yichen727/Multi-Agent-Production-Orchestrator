# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MAPO (Multi-Agent Production Orchestrator) is a LangGraph multi-agent system for film/video post-production workflows. An MSc project (UCL CGVI). **Four** specialised ReAct agents form a strict linear pipeline — **Ingest → Search → Selection → Delivery** — driven as a **fixed state machine** (there is **no LLM supervisor**; an explicit orchestrator invokes one agent per stage) and exposed through a Streamlit UI. The metadata database is SQLite, **persisted to a file** (`settings.METADATA_DB_PATH`) so real ingested rows survive app restarts (the demo catalogue is seeded only when the DB is empty, and is replaced by real data when the user runs ingest): ingestion genuinely probes each file with ffprobe (dimensions, orientation, fps, codec, audio, duration), runs FFmpeg scene-cut detection, and sends sampled frames to **GPT-5.4 Vision** for tagging (shot type, objects, keywords, description, approximate people count). Whisper transcription and face/speaker *identity* recognition are intentionally **not** implemented. The guiding rule everywhere: **store only what a tool measured or the vision model actually saw; leave the rest `unclassified`; never fabricate** (PostgreSQL remains the aspirational production datastore). Every catalogue query/resolution is **scoped to the current `project_id`**, so one project can never see or compile another project's media.

**Ingestion is temporal event-based (not just frame/clip-based).** Beyond the per-clip summary ("what is *in* the clip"), Ingest segments every clip into ordered **events** — the "what *happens*" layer — each with real start/end timecodes (from FFmpeg scene boundaries, never model-guessed), an action description, and its own embedding, stored in a `clip_events` child table (one `shots` row → many events). Events are consumed along a **strict retrieval-vs-editing boundary**: **Search stays clip-level** — it returns whole clips, but recall is *event-aware* (`hybrid_search` folds each clip's best-matching event into that clip's relevance, so a clip surfaces when a moment inside it hits; the moment rides along as a `matched_event` hint but the unit is always the clip). **Selection is where moments get *cut*** — the agent decides, from the editing intent, whether to build a whole-clip timeline or a **moment-precise** one that trims to exact event boundaries (`get_clip_events` → `plan_moment_timeline`). Delivery compiles either with **no change** (it already honours per-segment in/out). Timecodes are always real measurements — the vision model only describes what happens inside a window it is told about; it never invents a timecode. (There is deliberately **no** "search moments" user mode and **no** UI moment-precise toggle — exposing moments in Search would leak an editing concern into retrieval; the agent chooses in Selection.)

The system is a clean AI-assisted editing pipeline — **Ingest builds the semantic knowledge base, Search retrieves candidates via hybrid recall, the editor curates which clips participate (a UI Human-in-the-Loop layer), Selection orchestrates those curated clips into a narrative edit timeline, and Delivery compiles that timeline into a Premiere Pro–importable project file.** It was refactored from an earlier 6-agent design, then a 4-agent two-phase design: the Metadata Agent was renamed to the **Ingest Agent**, and the **Quality Agent was removed entirely** (quality is now the editor's judgement, informed by the Selection Agent's reasoning — there is no automated scoring agent). The **Delivery Agent** was then (re)introduced as the 4th, final stage: a pure project compiler (no creative editing/ranking). Of the earlier removed modules only `delivery_agent` came back; the rest stay deleted, and a test asserts they are no longer importable.

## Commands

```bash
pip install -r requirements.txt    # install deps
python main.py                     # launch — the ONLY supported entry point (spawns streamlit)
streamlit run app/ui/streamlit_app.py   # equivalent direct launch

pytest tests/ -v                   # run all tests
pytest tests/test_agents.py::test_shot_query -v   # run a single test
```

Requires an `OPENAI_API_KEY` in `.env` (already present in this workspace). FFmpeg/ffprobe must be on PATH for ingest proxy/frame tooling to work — if absent, those tools return graceful error strings rather than crashing.

## Architecture

The system is assembled in [app/orchestrator/production_orchestrator.py](app/orchestrator/production_orchestrator.py) — read this first; it's the spine that ties everything together.

**Two layers (fixed-pipeline orchestration — no supervisor):**

1. **Pipeline orchestrator** — [production_orchestrator.py](app/orchestrator/production_orchestrator.py) drives MAPO as an explicit four-stage state machine. There is **no LLM supervisor** and **no top-level `mapo_agent` graph** (both were removed): the module exposes four explicit stage functions — `run_ingest`, `run_search`, `run_selection`, `run_delivery` — each invoking exactly one compiled sub-agent (or, for Search, `retrieval_service.hybrid_search` directly). It owns the shared `_base_state` / `_config` helpers and `_extract_plan` (see below). The UI calls these functions in order, so the code path, the architecture diagram, and the thesis description all match (no "documented supervisor, actually bypassed by the UI" discrepancy).

   **Human-in-the-Loop** is ONE mechanism: the editor's direct control in the UI — the **curation checkboxes** (which candidate clips participate) plus the explicit **Export** button (which triggers Delivery). There is no LangGraph `interrupt()` approval gate (the old `verify_project` / `human_approval_gate` / `_needs_approval` were dead code — they fired on state fields no agent wrote and the UI never resumed them — and were deleted).

2. **Four sub-agents** in [app/agents/](app/agents/), each a self-contained ReAct loop (`assistant → tools → assistant`) compiled by the `_build_agent_graph` helper. The pipeline is linear: `ingest_agent` → `search_agent` → `selection_agent` → `delivery_agent`. The strict order (Search/Selection/Delivery only after Ingest) is enforced by the **UI**, which locks the later phases until Ingest reports a structured success.

**Project isolation & identifier resolution.** `project_id` reaches the tools via LangGraph `InjectedState` (annotated `state: Annotated[dict, InjectedState]`), so the model never fills that security-boundary argument — the ToolNode injects it from `ProductionState`. Selection and Delivery resolve shot-id/file-name identifiers through the shared [catalogue_resolver.py](app/services/catalogue_resolver.py), which filters every query by `project_id` and raises `AmbiguousIdentifier` (listing candidates) instead of silently taking the first match when a file name is ambiguous.

### The four agents

Each agent is **self-contained**: it defines its own `@tool` functions, the `<name>_tools` list, the assistant node, and the router. There are exactly four agent modules — the earlier `metadata_agent`/`quality_agent`/`shottagger_agent`/`gradebot`/`selectbot` modules were renamed/removed and **deleted** (one source of truth, no fallback path). A test asserts those modules are no longer importable. (`delivery_agent` was later re-added as the 4th stage and now imports cleanly.)

| Agent ([file]) | Responsibility | Owns tools |
|---|---|---|
| [ingest_agent.py](app/agents/ingest_agent.py) | Scan, probe, vision-tag, **embed**, **extract temporal events**, catalogue (SQLite + JSON) — builds the searchable semantic knowledge base (clip- and event-level) | `detect_new_footage`, `ingest_footage` (full pipeline: ffprobe metadata + scene-cut detection + GPT-5.4 Vision tagging incl. semantic dims `camera_motion/lighting/mood/subject_position` + a semantic embedding → DB; **plus temporal event extraction** — `_build_clip_events` segments the clip via `build_event_windows` (scene cuts + long-scene sub-division) and calls `analyze_event` per window for the "what happens" tags + a per-event embedding, persisted to `clip_events`; **incremental** — unchanged files (and their events) reused via `source_mtime`/`source_size` fingerprint, `force_reanalyze=True` to override; `analyze_events=False` to skip the event layer), scan/verify/proxy/structure, shot queries (`get_shots_by_type`, `classify_shot_attributes`), `export_metadata_json`. Reads the footage directory + `project_id` from injected **state** (not a mutated global). Records a structured **`IngestResult`** (`success`/`partial_success`/`failure` + `indexed_count` + `event_count`) that the UI gates on; **refuses** (no destructive rewrite) when the scan exceeds the per-run file cap. |
| [search_agent.py](app/agents/search_agent.py) | **Retrieval only, CLIP-level** — returns candidate clips + suggestion marker + grounded relevance %, never moments/timecodes and never picks "best" | **`search_catalogue`** (event-aware clip hybrid: wraps `retrieval_service.hybrid_search` — SQL hard filters + vector semantic recall with lexical fallback, and folds each clip's best-matching event into its relevance so a moment can surface its parent clip; the moment rides along as a `matched_event` hint only), `list_all_shots` (ground-truth, project-scoped). The LLM just fills structured query params; `project_id` injected from state. **No `search_moments` tool** — choosing a moment is Selection's job (retrieval-vs-editing boundary). |
| [selection_agent.py](app/agents/selection_agent.py) | Intent-aware **edit-timeline orchestrator** (NOT a score ranker) — chooses a timeline structure that fits the editing intent (NO fixed narrative arc; any number of "Timeline Steps") and explains each step's placement/connection/pacing | `get_candidate_details` (by shot_id OR file path), `get_clip_events` (list a clip's temporal events + timecodes), **`plan_timeline`** (turns the ordered clips + per-clip importance into structured **segments** via [timeline_service](app/services/timeline_service.py): **TRIM MODE** per-clip head/tail trim, **TIMED MODE** trims + allocates screen time proportionally to importance, else **FULL CLIP MODE**), **`plan_moment_timeline`** (ordered event_ids → **EVENTS MODE** segments trimmed to each event's own in/out via `plan_event_segments`), `generate_delivery_summary`. Every planner emits a fenced ```json plan carrying per-segment `valid`/`validation_error`. Resolution is **project-scoped**; it **refuses** (never silently drops) unresolved/ambiguous identifiers/event-ids. Consumes the editor's **curated** clips, not raw Search output. |
| [delivery_agent.py](app/agents/delivery_agent.py) | **Project compiler** (NOT an editor) — compiles the edit timeline into a Premiere Pro–importable project file. Preserves clip order + trims exactly; makes no creative/ranking decision | **`compile_timeline_segments`** (preferred — consumes the `plan_timeline` JSON directly, honouring per-segment in/out trims; **refuses** any segment flagged `valid: false`), `compile_premiere_project` (ordered clips → sequential time mapping, full clips), `preview_delivery_timeline` (dry-run). All resolve ordered clips (**project-scoped** via `catalogue_resolver`) → **FCP7 XML `xmeml` v5** that Premiere imports natively + JSON intermediate, written to `PROCESSED_OUTPUT_DIR/exports`. Tracks: V1 video, A1 original audio, A2 secondary audio only when a clip truly has a 2nd audio stream. Backed by [app/services/premiere_export_service.py](app/services/premiere_export_service.py) (`build_timeline`/`to_fcp7_xml`/`compile_project`; per-clip `in_point`/`out_point`). Refuses to compile if any identifier does not resolve to a real catalogued clip, or is ambiguous — never fabricates a media reference. |

There is no automated quality scoring agent — quality is the editor's judgement, supported by the Selection Agent's explanations. (The `quality_score`, `scene_number`, and `take_number` columns were dropped from `shots` — they were always `NULL` on real ingested rows, so the `filter_low_quality` Selection tool and the scene-based Ingest query tools that depended on them were removed too.)

**Every agent follows the same three-part contract** — when adding or editing an agent, preserve this shape because the orchestrator imports these three names per agent:
- `@tool`-decorated functions + a `ToolNode`,
- `<name>_assistant(state, config)` — binds tools to the LLM, prepends a `SystemMessage` prompt, returns `{"messages": [response]}`,
- `should_continue_<name>(state, config)` — returns `"continue"` if the last message has `tool_calls`, else `"end"`.

### Shared state

[app/models/state.py](app/models/state.py) defines `ProductionState` (a `TypedDict`), the single state object threaded through the graph. Its fields are **typed against the Pydantic contract** in [schemas.py](app/models/schemas.py) (`search_candidates: list[SearchCandidate]`, `edit_timeline: Optional[EditPlan]`, `delivery_output: Optional[DeliveryResult]`, `footage_dir: str`, etc.). `messages` uses the `add_messages` reducer; `remaining_steps` (`RemainingSteps`) guards against infinite ReAct loops. `footage_dir` carries the run's footage directory on state (so concurrent sessions don't clobber a global). Add new state fields **additively** to stay backward-compatible. (There is no approval gate — HITL is the UI, see above.)

### Services (shared singletons)

- [app/services/openai_service.py](app/services/openai_service.py) — exports module-level `llm` (and `llm_fast`), plus embedding helpers `get_embeddings()` / `embed_texts(texts) -> list[list[float]] | None` (`settings.EMBEDDING_MODEL`, returns `None` without a key/on failure — never a fabricated vector). **Import `llm`/`embed_texts` from here**; agents bind tools via `llm.bind_tools(...)`. Don't construct `ChatOpenAI`/`OpenAIEmbeddings` directly in agents.
- [app/services/retrieval_service.py](app/services/retrieval_service.py) — **hybrid retrieval**: `hybrid_search(project_id, *, keywords, shot_type, orientation, people, min_duration, max_duration, top_k)` is the Search stage's entry — it returns whole-**clip** candidate dicts (metadata + `relevance` + `group_size` + `suggestion` + a `matched_event` hint when a moment drove the match), always `project_id`-scoped. SQL hard filters → clip vector cosine (numpy) → lexical fallback, **AND** an *event-aware* layer: `_best_event_by_path` scores each surviving clip's `clip_events` (restricted to the filtered clips) and folds the best event into the clip's relevance with the same noisy-OR rule, so a moment can surface its parent clip — but the unit returned is always the clip. **`search_events(project_id, *, keywords, shot_type, orientation, top_k)`** is the moment-level primitive (returns each event's timing/action + parent-clip context + `relevance` + `suggestion`); it now backs the **Selection** stage, **not** a Search user mode. Both share one event-scoring path (`_score_events`). The Search Agent's `search_catalogue` **and** the orchestrator's `run_search(query, project_id)` (called by the UI) go through `hybrid_search`, so retrieval is identical LLM-driven or user-driven. Also exports `expand_query`, `hoist_orientation`, `group_size(people_count)`.
- [app/services/catalogue_resolver.py](app/services/catalogue_resolver.py) — **project-scoped identifier resolution** shared by Selection & Delivery. `resolve_one(project_id, token)` / `resolve_ordered(project_id, tokens)` turn a shot-id or file path/name into exactly one real catalogued row **within that project** (numeric ids and file names both scoped). Matching is most-specific-first (exact path → exact basename → substring); a name matching >1 clip raises `AmbiguousIdentifier` (never silent first-match). Returns `None` (never fabricates) when nothing matches; `resolve_ordered` returns `(rows, problems)` so callers refuse rather than proceed on any unresolved/ambiguous token.
- [app/services/database_service.py](app/services/database_service.py) — exports singleton `db` (a LangChain `SQLDatabase`, read path) **and** module-level write helpers `replace_project_shots(project_id, rows)` / `get_catalogued_paths(project_id)` / `get_catalogued_shots(project_id)` over the underlying `_engine` (this is how real ingested rows enter the catalogue). `_create_engine()` opens the connection with PRAGMAs `foreign_keys=ON`, `busy_timeout`, and `journal_mode=WAL` (file DBs), persists to `settings.METADATA_DB_PATH`, and seeds the demo catalogue only when empty (tests set the path to `:memory:` via `tests/conftest.py`). The `shots` schema (`_SCHEMA_DDL`) has a `UNIQUE(project_id, file_path)` constraint and indexes on `project_id`/`orientation`/`shot_type`/`duration_seconds`; it carries real-metadata columns (`width/height/orientation/fps/codec/has_audio/scene_count/description/people_count`) plus semantic columns (`camera_motion/lighting/mood/subject_position/embedding`, embedding = JSON float list). A child **`clip_events`** table (temporal events) has a `shot_id` FK **`ON DELETE CASCADE`**, so `replace_project_shots`' `DELETE` of a project's shots also clears its events (which `foreign_keys=ON` would otherwise reject); its event write/read helpers are `replace_project_events(project_id, events)` (resolves each event's `shot_id` from `(project_id, file_path)` of the freshly-written shots — call it AFTER `replace_project_shots`; skips events whose file has no shot), `get_catalogued_events(project_id)` (grouped by file, for reuse), and `get_events_by_ids(project_id, ids)` (project-scoped, joins `source_duration`). `_EVENT_COLUMNS` is the write contract for `clip_events`. `replace_project_shots` creates the parent `projects` row (`INSERT OR IGNORE`) before inserting shots so the FK holds. `_SHOT_COLUMNS` is the contract for `replace_project_shots` — keep it in sync with the table. Tests assert against the demo seed (5 shots, shot 3 is `close_up`, all demo rows `landscape`; note shots 1 & 4 share the basename `take01.mov`, which the resolver treats as ambiguous) — changing the seed will break tests. **New tables** (like `clip_events`) DO get created on an existing file DB (`CREATE TABLE IF NOT EXISTS` runs each launch), but `UNIQUE`/column changes to an EXISTING table need an `ALTER` migration (see `_migrate_shot_columns`); indexes apply retroactively. The `quality_assessments`/`transitions` tables are legacy/unused.
- [app/services/ffmpeg_service.py](app/services/ffmpeg_service.py) — subprocess wrappers: `probe_video_metadata` (dims/orientation/fps/codec/audio/duration, rotation-aware), `detect_scene_cut_times`/`detect_scene_count` (FFmpeg scene-change cut timestamps/count), `extract_sample_frames_b64` (in-memory frames for vision), plus — for the event layer — `build_event_windows(duration, cut_times, ...)` (turns scene cuts into ordered `(start,end)` event windows, sub-dividing long continuous shots and capping the count) and `extract_frames_in_window_b64(path, start, end, count)` (several ordered frames from ONE window so the model can see the change), plus proxy generation, frame extraction, duration probing. All degrade gracefully when FFmpeg/ffprobe is absent.
- [app/services/vision_service.py](app/services/vision_service.py) — `analyze_frames(frames_b64) -> VisionTags | None`: clip-level GPT-5.4 (`settings.VISION_MODEL`) tags via `.with_structured_output(VisionTags)`. **`analyze_event(frames_b64, start_seconds, end_seconds, clip_duration) -> EventTags | None`** is the temporal counterpart: it is given SEVERAL ordered frames from ONE event window and an **action/change-oriented** prompt ("what HAPPENS across these frames, in order"), returning `EventTags` (`action`/`state_change`/`subjects`/`keywords`). Both return `None` (so the caller leaves fields unclassified) when there's no API key/frames or the call fails — they never fabricate, and the model is only told the window bounds, never asked to invent timecodes.
- [app/services/timeline_service.py](app/services/timeline_service.py) — the Selection-stage **timeline planner** (pure, no LLM/IO). `parse_target_duration(text)` detects a target length in free text ("15s", "1 min", "2 minutes", "1:30" → seconds, else `None`); `allocate_durations(sources, weights, target)` water-fills the target across clips proportionally to importance, capping each at its real length and redistributing the surplus; `plan_segments(clips, target, weights, head_trim, tail_trim)` returns the structured plan (`mode` = `trim`/`timed`/`full`, per-segment `in_point`/`out_point`, order preserved); **`plan_event_segments(events, labels)`** is the event-based planner (`mode='events'`) — each segment's in/out are the event's own measured `start_seconds`/`end_seconds`. Each segment carries **`valid`/`validation_error`** and the plan a top-level **`valid`/`validation_errors`**: a clip with real footage but nothing left after trimming (or an event range outside the source) is flagged invalid (not silently emitted or dropped) so Delivery refuses it. The Selection Agent's `plan_timeline`/`plan_moment_timeline` tools wrap these — both emit the SAME plan shape, so Delivery compiles them identically.
- [app/services/premiere_export_service.py](app/services/premiere_export_service.py) — the Delivery-stage **compiler** (pure, no LLM). `build_timeline(clips, ...)` maps ordered, resolved clips into a neutral JSON intermediate (frame-accurate sequential in/out + sequence positions; order preserved exactly); an explicit illegal trim (zero/negative length, or outside the measured source) raises **`InvalidSegmentRange`** naming the segment — the full clip is used ONLY when neither in- nor out-point is given (it is never silently expanded). `to_fcp7_xml(timeline)` renders it as valid FCP7 `xmeml` v5 (Premiere imports natively) with V1/A1/A2 tracks; `compile_project(...)` combines both and writes `.xml` + `.json` to `PROCESSED_OUTPUT_DIR/exports`. Raises rather than emit a clip without a real `file_path`. The Delivery Agent's tools call these directly.

### UI

[app/ui/streamlit_app.py](app/ui/streamlit_app.py) is the user-facing layer and the **Human-in-the-Loop control layer**. It is a **thin presentation layer**: every stage goes through the pipeline orchestrator's explicit stage functions (`_orch().run_ingest/run_search/run_selection/run_delivery`) — there is no supervisor and no direct sub-agent wiring in the UI. It presents the pipeline as gated phases — ① Ingest → ② Search → ③ Selection → ④ **Deliver** (curation happens continuously via the sidebar Bin checkboxes) — where everything after Ingest stays disabled until `st.session_state.ingest_done` is set ("Reset Pipeline" clears all session state). Key flows:
- **Ingest** calls `run_ingest(footage_path, project_id, user_id)`, which passes the directory on state (no global mutation). It unlocks the later phases **only** on a structured `IngestResult` with `status` `success`/`partial_success` **and** `indexed_count > 0` **and** an independent catalogue-count check — a non-empty agent message (e.g. "Directory not found") never unlocks anything (audit C-08).
- **Search** calls `run_search(query, project_id)` (shared query understanding + event-aware `hybrid_search`) — always CLIP-level, no granularity switch; the **curation layer** renders each candidate as a checkbox + suggestion marker (🟡/⚪/🔴) + preview, and when a moment drove the match the card's reason shows the `matched_event` ("contains: … @start–end"). Only the ticked `selected_candidates` (file paths) are handed to Selection.
- **Selection** calls `run_selection(...)` — no moment-precise toggle; the **agent itself** decides from the editing intent whether to use `plan_timeline` (whole-clip) or `get_clip_events` + `plan_moment_timeline` (EVENTS MODE). The orchestrator reads the structured plan from the planning **ToolMessage** (`plan_timeline` or `plan_moment_timeline` — the tool's own output, which the model can't rewrite) via `_extract_plan`, and the UI stashes it in `st.session_state.last_timeline_plan`.
- **Deliver** is enabled **only** when a structured plan with `segments` exists (there is **no media-pool-order fallback**, audit H-04); it calls `run_delivery(plan, ...)`, which requires the plan and compiles its ordered segments via `compile_timeline_segments` (trims + order preserved).

The sidebar Bin has a **Select-all** toggle (an `on_change` callback that ticks/unticks the whole pool without fighting manual picks). Each stage renders its **own output inline** (timeline under ③ Selection, export result under ④ Deliver); the running agent transcript is demoted to a **collapsed "🛠️ Debug log"** at the bottom. The orchestrator is lazy-imported (to avoid recompiling on every rerun).

## Conventions

- Tool docstrings are the agent's API contract — the LLM selects and fills tools based on them. Write them precisely (args + return description).
- Ingestion is real (ffprobe + FFmpeg scene detection + GPT-5.4 Vision); PostgreSQL is still the only simulated/aspirational piece.
- **Never fabricate catalogue data.** Tools return real measurements or `None`/`unknown`; agent prompts forbid inventing filenames, scores, or tags. If you add a tool or prompt, preserve this — it's the fix for the agents hallucinating clips that don't exist.
- `pydantic` schemas in [app/models/schemas.py](app/models/schemas.py) define the stage-to-stage data contract: `SearchCandidate` (mirrors a `hybrid_search` row), `TimelineSegment`/`EditPlan` (mirror `plan_segments`, incl. `valid`/`validation_error`), `IngestResult` (ingest outcome the UI gates on, incl. `event_count`), `DeliveryResult` (compile outcome), `VisionTags` (clip-level, enforced by the vision model) and **`EventTags`** (action-oriented per-event output) / **`ClipEvent`** (a persisted `clip_events` row), plus `ShotMetadata`, `EditingIntent`, etc. `ProductionState` is typed against these. Note: both `VisionTags` and `EventTags` deliberately avoid a field literally named `description` and give every field an explicit `Field(description=...)` — that is the fix for the structured-output schema-echo bug; preserve it when editing either. The Selection→Delivery hand-off still travels as the `plan_timeline` JSON (read from the ToolMessage, not model prose), and `IngestResult` travels via an in-process registry (`get_last_ingest_result`); full instance validation at every tool boundary is still being rolled out — treat the schemas as the intended, mostly-wired contract.
- Search vs. Selection vs. Delivery is a hard responsibility boundary: Search **retrieves candidates only** (hybrid recall, no "best" pick); Selection **orchestrates the editor's curated clips into an intent-driven edit timeline** — it chooses whatever structure/pacing/length best fits the stated editing intent (NO fixed narrative arc; "Timeline Steps", not mandatory roles) and explains each step, it does not rank by score; Delivery is a **pure compiler** — it turns the finished timeline into an importable Premiere project and **must never re-order, drop, trim, or otherwise edit** clips (order in = order out). Keep retrieval/ranking logic out of Selection, "best take"/timeline logic out of Search, and any creative/ranking logic out of Delivery.
